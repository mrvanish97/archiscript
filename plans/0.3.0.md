# 0.3.0: architectural resolution and actionable checks

Status: proposed plan and findings, not implemented. The current package remains
at **0.2.0**. This plan follows the original design documents; it does not
reinstate a taxonomy requirement.

## Assessment after realignment

ArchiScript's strongest idea is choosing architectural distinctions and checking
what remains valid as those distinctions are composed or changed. Subdomains
describe semantic regions; VDPs select finite, exhaustive, disjoint members at a
chosen resolution; operations map those members. Supporting subdomains may
overlap, intersect, and contribute to several resolutions of the same carrier.

The 0.2.0 realignment removes the tree requirement and missing-tree warning,
keeps correspondence evidence outside partition identity, and demonstrates four
field-presence combinations grouped into two members. This restores the
foundation's intended distinction between regions and architectural members.

Member operations intentionally do not determine value-level programs. Missing
value selection is a separate contract/implementation concern, not a defect in
the partial-member-function definition. See the foundation's
[carrier relation and lifts](../../archiscript-docs/chapter-1/stage-1/foundation.tex).

## First milestone: check whether a coarsening is safe for a consumer

The foundation defines refinement and coarsening, but the current library only
demonstrates a particular coarsening through a manually written operation and
classification theorem. Generalize that capability before expanding the ontology.

For partitions $P$ and $Q$ of the same carrier, represent a coarsening by a total
surjective member map $q$ with checked classification correspondence:

\[
Q(x) = q(P(x)).
\]

Given a consumer $f : \mathcal M_P \rightharpoonup \mathcal M_Y$, determine
whether there is a consumer $g : \mathcal M_Q \rightharpoonup \mathcal M_Y$
satisfying $f = g \circ q$. The required condition is:

\[
q(a) = q(b) \Longrightarrow f(a) = f(b).
\]

Equality includes definedness: merging an undefined case with a defined case
also prevents this factorization. For executable finite member maps, return a
checked factorization or a concrete pair of conflicting input members. Do not
infer value-level information loss merely from merging member distinctions:
the underlying carrier values stay unchanged.

Acceptance criteria:

- A consumer that only accepts complete forms factors through the two-member
  partition in [FormInput](../ArchiScript/Examples/FormInput.lean).
- A consumer that distinguishes missing email from missing name fails, with
  those two members reported as the conflicting pair.
- A defined/undefined mismatch within one coarse member is also rejected.
- The positive result includes correspondence evidence usable by composition;
  a negative result identifies the actual conflicting mappings.
- No tree requirement or change to the partial-function law is introduced.

## Other findings and candidate follow-ups

### 1. Make the natural authoring path carry its evidence

[`Partition.Realizes`](../ArchiScript/Partition.lean) connects named predicates
to classifier fibers, but authors currently supply it separately. A model can
compile while separately named domains have no checked connection to its members.

Consider a constructor accepting selected regions and their partition evidence,
returning the partition together with checked correspondence. Keep the low-level
classifier API. Support grouped and overlapping supporting subdomains; only the
selected members need to satisfy partition obligations. Reduce duplicated
declarations and routine proof work without forcing a new presentation format.

### 2. Preserve the justification for completeness claims

The original `unjustified-generalization` diagnostic targets unsupported boundary
claims. It cannot reliably be inferred from the spelling of a set expression:

\[
U \setminus (A \cup B) = (U \setminus A) \setminus B.
\]

Track why a boundary is exhaustive: an external requirement, an established
domain law, or explicitly exhaustive constructors. Diagnostics should identify
the unsupported claim and its provenance. A flat declaration, union, or Lean
`inductive` is not itself a design error. Arbitrary predicates do not encode all
the authorial intent required for this check.

### 3. State the context in which membership is fixed

Observation narrows knowledge about a fixed semantic occurrence. Environmental
change can instead change the underlying state: the same URI may have required
sibling files today and lack them tomorrow.

Adopt an explicit context or snapshot convention for filesystem and database
predicates. The original `SemVerRange × NpmEnv` example already provides a useful
pattern. This does not require hydration operations or a PVDP when topology is
unchanged. Clarify what is held fixed before asserting membership or combining
observations.

### 4. Turn finite facts into architecture findings

For executable member maps, derive undefined inputs, unreachable targets,
merged distinctions, and counterexamples to claimed path equivalence.

Whole-model checks additionally need an enumerable model scope, declared
appearances, and explicit obligations. The current
[`Operation.Registry`](../ArchiScript/Operation.lean) resolves names but does
not enumerate the architecture; branch names need not cover all defined edges.
Ownership tags record responsibility without establishing that every relevant
branch has been inspected.

Preserve the original result states: **proved**, **disproved**, **conditional**,
and **unknown**. Unsupported analysis and unresolved assumptions must not be
reported as proof. Avoid pressuring authors to invent assumptions simply to
make a partial design compile.

### 5. Clarify the empty-image case in the mathematical foundation

VDPs have nonempty carriers and member sets. A nowhere-defined operation is
allowed, but its image is empty. The paper's factorization through the image
therefore has an intermediate object that is not an admissible VDP in this case.

Distinguish factorization in the ambient category of finite sets and partial
functions from factorization inside the VDP category, or qualify the latter
for nonempty images. Resolve this before implementing general image
factorization; do not silently change VDP nonemptiness.

### 6. Strengthen value-level contracts where the requirement needs them

The [registration contract](../ArchiScript/Examples/UserRegistration.lean)
permits selecting a different existing user: input user 7 and output user 8 can
satisfy its current premises. Its no-creation theorem still proves its stated
claim. Add the missing identity relationship when modeling selection correctness,
and keep this obligation distinct from the member calculus.

## Evaluation and scope

Prioritize the consumer/coarsening milestone. The other findings are tracked
candidates, not a commitment to implement every capability in 0.3.0.

Use examples with seeded design defects and assess whether diagnostics change
an architectural decision. Compare prose alone, the authoring skill alone, and
the skill plus checker. Measure defects found, explicit unresolved assumptions,
and review effort; compilation success alone does not establish product value.

The expected value is a clearer shared implementation contract and actionable
counterexamples before production work. That benefit is plausible from the
foundation and examples, but has not yet been established by comparative trials.
