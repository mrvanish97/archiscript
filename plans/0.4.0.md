# 0.4.0: compositional alternatives and semantic resolution

Status: planned.

ArchiScript 0.3.x establishes strict Value-Domain Partitions (VDPs), ordinary
partial-member Operations, sequential composition, and the symmetric monoidal
tensor for independent semantic coordinates.

Version 0.4.0 should extend that calculus conservatively. The release should add
only mathematically conventional structure whose meaning is predictable from
standard category/order theory and whose proof obligations remain local and
lightweight.

The release has two primary goals:

- add coproduct as lossless structural OR for already justified alternative
  VDPs;
- add refinement/coarsening analysis and consumer factorization over existing
  VDPs and Operations.

The release should not introduce a standardized ontology of time, failure,
availability, consistency, observation, ownership, or other software
architecture concepts. Those remain user-defined semantic domains.

## Governing principle

ArchiScript standardizes the form of architectural reasoning, not the contents
of the architecture's vocabulary.

New mathematical names must retain their conventional mathematical meanings.

In particular:

- tensor remains a symmetric monoidal tensor, not a categorical product;
- coproduct must satisfy the categorical coproduct universal property;
- refinement/coarsening remains the standard order on partitions of one
  carrier;
- coarsening does not follow merely from a total surjective member map;
- factorization means ordinary morphism factorization through an existing map.

Prefer new constructors and derived theorems over new architectural entity
kinds.

## Existing core remains unchanged

0.4.0 preserves the established meanings of:

- Domain and semantic subdomains;
- Partition / VDP;
- Operation as a partial function between finite member families;
- sequential composition;
- independent tensor;
- PVDP parameterization;
- appearance, review, provenance, responsibility, bindings, and evidence.

PVDP remains available but is not a focus of this release. Its narrow meaning
remains unchanged: a parameter is architecturally relevant when changing its
member changes which outbound operations exist from at least one
specialization.

## 1. Coproduct: lossless structural OR

### Motivation

Tensor already provides a canonical lossless composition for simultaneous
independent coordinates:

    P ⊗ Q

with carrier:

    Carrier(P) × Carrier(Q)

0.4.0 should add the corresponding canonical construction for tagged
alternatives:

    P ⊕ Q

with carrier:

    Carrier(P) + Carrier(Q)

and member family:

    Members(P) + Members(Q)

The classifier follows the sum tag:

    inl p -> inl (P.classify p)
    inr q -> inr (Q.classify q)

The result is still an ordinary Partition.

### Meaning

Tensor is structural AND:

    P ⊗ Q

means that both independent coordinates are present.

Coproduct is structural OR:

    P ⊕ Q

means that exactly one tagged alternative is present, while preserving which
summand and which member inside that summand was selected.

Coproduct is lossless. It does not coarsen either source VDP and does not erase
the source tag.

For example:

    UserCommand
    ├── Create
    ├── Update
    └── Delete

    SystemCommand
    ├── Reconcile
    └── Expire

may be composed as:

    Command := UserCommand ⊕ SystemCommand

without flattening or forgetting the original distinctions.

A high-level diagram may render Command as one collapsed node and expand it on
demand. That is loss of presentation detail only; the model retains the full
tagged structure.

### Categorical requirement

The coproduct name is justified only if the standard universal property is
proved.

Provide canonical injections:

    inl : Operation P (P ⊕ Q)
    inr : Operation Q (P ⊕ Q)

For any Operations:

    f : Operation P R
    g : Operation Q R

provide a unique copairing:

    [f,g] : Operation (P ⊕ Q) R

such that:

    [f,g] ∘ inl = f
    [f,g] ∘ inr = g

The uniqueness theorem is part of the public mathematical contract.

The implementation should also provide the ordinary functorial map on
coproducts where useful:

    f ⊕ g :
      P ⊕ Q -> P' ⊕ Q'

with identity and composition laws proved pointwise.

### Boundary-safety rule

Coproduct must never be treated as evidence that the selected summands exhaust
an external boundary.

The key rule is:

    P ⊕ Q is exhaustive over Carrier(P) + Carrier(Q).

    It is not evidence that Carrier(P) + Carrier(Q)
    exhausts an independently supplied external universe.

This distinction is essential to ArchiScript's deductive modeling discipline.

For example, observing two known external message kinds does not justify:

    ExternalInput := PaymentMessage ⊕ RefundMessage

unless an independent boundary contract already establishes that every input is
one of those two tagged alternatives.

Otherwise coproduct would become an inductive backdoor: convenient known cases
would define the carrier, and coverage would become tautological while unknown,
unsupported, malformed, or future cases disappear from the model.

Constructor closure therefore remains distinct from external boundary
completeness.

### Intended architectural use

Coproduct is primarily for lossless structural aggregation of already justified
alternative VDPs.

It is not introduced as:

- a replacement for defining one natural VDP directly;
- an if/else primitive;
- evidence of external exhaustiveness;
- semantic coarsening;
- a way to erase detail.

If alternatives already belong naturally to one carrier and one VDP, define
that VDP directly.

Use coproduct when independently meaningful VDPs should be composed as tagged
alternatives while preserving their identities and existing Operations.

## 2. Refinement and coarsening as properties of existing VDPs

The mathematical foundation already defines refinement for VDPs over the same
carrier.

For P and Q on the same carrier:

    P ≼ Q

means that P is finer than Q and Q is a coarsening of P.

Strictly:

    for every M in Members(P),
    there exists N in Members(Q)
    such that M is a subset of N.

Because Q is a partition, that N is unique.

Therefore there is a unique canonical map:

    q[P,Q] : Members(P) -> Members(Q)

such that:

    M is a subset of q[P,Q](M)

for every fine member M.

Since both VDPs cover the same carrier and all selected members are inhabited,
the canonical map is automatically surjective.

### Important non-equivalence

A total surjective Operation:

    q : Operation P Q

is not sufficient to establish coarsening.

A total surjective member map may pair fine and coarse labels even when a fine
semantic region is cut across multiple Q members.

Coarsening requires semantic containment:

    M is a subset of q(M)

for every member M of P.

This is the essential property.

### API direction

Do not introduce refinement or coarsening as new architectural object kinds.

Expose them as propositions, witnesses, and derived Operations over existing
Partitions.

The natural authoring shape should be conceptually:

    prove P ≼ Q
        ↓
    derive the unique total coarsening Operation P -> Q

The Lean representation may use classifiers internally, but the public
mathematical meaning should remain extensional containment of semantic members.

## 3. Consumer factorization through a coarsening

The main practical payoff of refinement in 0.4.0 is to determine whether a
consumer really needs the fine semantic distinctions.

Given a proven coarsening:

    q : P -> Q

and a consumer:

    f : P -> Y

ask whether there exists:

    g : Q -> Y

such that:

    f = g ∘ q

Because q is surjective, such g is unique when it exists.

The necessary and sufficient condition is:

    q(a) = q(b)  ->  f(a) = f(b)

for all fine members a and b.

Equality includes definedness. Therefore a fine member mapped by f to none and
another mapped to some target cannot be merged when both coarsen to the same Q
member.

### Executable finite analysis

Member families are finite, so this check should be executable.

For each coarse member:

1. enumerate its fine preimage under q;
2. compare f on every fine member in that fiber;
3. if all results agree, use that result to construct g;
4. otherwise return two concrete conflicting fine members.

Positive result:

    factors
      derived g : Operation Q Y
      proof f = g ∘ q

Negative result:

    conflict
      left fine member
      right fine member
      proof they coarsen together
      differing consumer results

This is more valuable than a Boolean result because both outcomes are directly
useful in architecture review.

## 4. Semantic zoom for diagrams and review

Consumer factorization should feed directly into review and diagram
projections.

If every selected outgoing consumer from a fine VDP factors through the same
coarsening, a high-level diagram may safely replace the fine VDP with the coarse
VDP for that view.

For example:

    DetailedForm
    ├── MissingEmail
    ├── MissingName
    ├── MissingBoth
    └── Complete

may coarsen to:

    Form
    ├── Invalid
    └── Complete

For a consumer that maps all three invalid cases to Reject, ArchiScript may
derive:

    Invalid  -> Reject
    Complete -> Accept

For a consumer that distinguishes MissingEmail from MissingName, the same zoom
is invalid. The analysis should return the conflicting pair rather than silently
simplifying the diagram.

This gives a precise distinction:

    coproduct
      = lossless structural grouping

    coarsening
      = intentional loss of semantic resolution

    consumer factorization
      = proof that the loss is safe for a selected view

Diagram simplification must therefore be a derived fact, not a presentation
heuristic.

## 5. Relationship between tensor, coproduct, and coarsening

0.4.0 should keep these operations sharply separated.

### Tensor

    P ⊗ Q

Structural AND.

- both independent coordinates are present;
- carrier is a Cartesian product;
- all product members remain present;
- lossless.

### Coproduct

    P ⊕ Q

Structural OR.

- exactly one tagged alternative is present;
- carrier is a disjoint/tagged sum;
- summand identity is preserved;
- lossless.

### Coarsening

    P ≼ Q

Semantic forgetting.

- P and Q classify the same carrier;
- complete fine members are merged into coarse members;
- a fine member may never be split across coarse members;
- semantic resolution is intentionally reduced.

These are different mathematical operations and should have different diagram
meanings.

## 6. What 0.4.0 should not add

### No domain ontology

Do not add foundational modules for:

- Time;
- Failure;
- Availability;
- Consistency;
- Communication;
- Resources;
- Trust;
- Policy;
- or similar architectural vocabulary.

Users define those semantics themselves through carriers, subdomains, VDPs,
and Operations.

### No observation primitive

Stage 2's semantic-superposition and observation vocabulary remains useful for
reasoning about knowledge, but 0.4.0 should not introduce a new foundational
Observation arrow.

If an architecture needs observer knowledge as explicit state, that knowledge
may be modeled as an ordinary user-defined carrier/VDP and transformed by
ordinary Operations.

A future release may revisit a generic epistemic construction only if real
models show that the ordinary calculus is insufficient.

### No member-dependent refinement primitive

A user may already define a finer VDP directly from semantic domains and prove
that it refines a coarser VDP.

Do not introduce a special member-dependent-refinement entity in 0.4.0.

A dependent constructor may be added later as an ergonomic helper if repeated
models demonstrate substantial proof duplication.

### No common-refinement commitment yet

The foundation already describes the meet/common-refinement construction for
partitions of one carrier. It remains mathematically valid and distinct from
tensor.

It is not required for the central 0.4.0 goals. Implement it only if the
coarsening work or concrete examples demonstrate immediate leverage.

### No broader category-theory framework

Do not turn ArchiScript into a general category-theory library.

Avoid adding products, equalizers, coequalizers, kernels, images, general
factorization systems, or other constructions merely because they are
mathematically available.

A standard construction enters the public calculus only when:

1. it has a canonical implementation in the existing category;
2. its defining law or universal property is inexpensive to prove;
3. it gives recurring architecture or diagram leverage;
4. its name can retain the conventional mathematical meaning exactly.

### No execution semantics

0.4.0 does not add:

- traces;
- temporal logic;
- runtime ordering;
- race/deadlock proofs;
- fairness;
- resource/effect semantics;
- distributed-system guarantees;
- implementation conformance.

Those require a separate behavioral model if they become necessary.

## 7. PVDP status

PVDP remains part of ArchiScript but is not expanded in 0.4.0.

Its current semantics remain:

    parameter member changes outbound operation topology
        -> PVDP

Ordinary data/environment changes, semantic refinement, coproduct grouping, and
diagram coarsening must not be redirected through PVDP.

The release should retain regression tests proving that the new constructions do
not weaken or reinterpret PVDP routing semantics.

## 8. Proposed implementation order

### Phase 1: coproduct of Partitions

Implement:

- Partition coproduct over Sum carriers;
- preservation of VDP nonemptiness, coverage, disjointness, and member
  inhabitance;
- canonical left and right injections;
- copairing of Operations;
- coproduct universal-property uniqueness;
- functorial mapping over coproducts where useful;
- identity/composition laws for that mapping;
- SemanticPartition support when source member meanings are available.

Add examples showing lossless diagram grouping of already justified alternative
VDPs.

Add a negative modeling example showing why coproduct construction alone does
not justify an external boundary.

### Phase 2: refinement/coarsening analysis

Implement:

- same-carrier refinement predicate;
- member-containment proof obligation;
- uniqueness of the coarse member containing each fine member;
- canonical total member map;
- automatic surjectivity theorem;
- induced ordinary Operation;
- reflexivity and transitivity of refinement.

Keep the public semantic statement based on member containment rather than
classifier implementation details.

### Phase 3: consumer factorization

Implement:

- executable finite factorization check;
- construction of the unique coarse consumer on success;
- proof of the commuting factorization equation;
- concrete conflicting fine-member witness on failure;
- defined/undefined mismatch detection.

Use the existing FormInput-style cases as positive and negative fixtures.

### Phase 4: review and diagram derivations

Expose enough checked information for tooling and skills to distinguish:

- tensor grouping;
- coproduct grouping;
- proven semantic coarsening;
- consumer-safe coarse views;
- concrete conflicts that prevent coarsening.

Diagram rendering remains a projection of checked model facts, not a new
semantic layer.

## 9. Acceptance criteria

0.4.0 is successful when all of the following hold:

1. P ⊕ Q constructs a valid ordinary VDP over a tagged sum carrier.
2. Coproduct injections and copairing satisfy the categorical coproduct
   universal property.
3. Coproduct preserves summand and member identity; it performs no semantic
   coarsening.
4. Coproduct construction is explicitly insufficient as evidence that its
   summands exhaust an external boundary.
5. P ≼ Q can be proved through semantic containment of fine members in coarse
   members on the same carrier.
6. The canonical coarsening member map is unique, total, and surjective.
7. The canonical coarsening map is available as an ordinary Operation rather
   than a new arrow kind.
8. Given f : P -> Y, ArchiScript can determine whether f factors through a
   proven coarsening P -> Q.
9. A successful factorization produces the unique coarse consumer and a proof
   of the commuting equation.
10. A failed factorization produces concrete fine members whose distinction the
    consumer requires.
11. Review/diagram tooling can use successful factorization as machine-checked
    justification for semantic zoom.
12. Tensor retains its existing full independent-product meaning and monoidal
    laws.
13. PVDP retains its existing narrow routing meaning and receives no new role.
14. No foundational API requires users to adopt ArchiScript-defined meanings
    for software-architecture domains such as time, failure, availability, or
    consistency.

The release should be judged by whether it increases compositional reuse and
machine-checked control over semantic resolution while keeping the foundational
ontology small and mathematically conventional.
