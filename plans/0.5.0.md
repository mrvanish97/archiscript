# 0.5.0: architecture expressions and certified local normalization

Status: implementation in progress.

ArchiScript 0.5.0 adds a finite presentation layer over the existing VDP /
Operation calculus. The release does not replace the category of VDPs and
Operations and does not make a graph foundational.

The release target is:

- typed expression semantics;
- finite expression families with one common source;
- conventional tensor/coproduct distributivity isomorphisms;
- certified local normalization by semantic equality or canonical structural
  transport;
- derived dependency / reachability / provenance foundations;
- examples and review guidance that distinguish normalization from architecture
  projection.

## Governing separation

A concrete architecture is described conceptually by

    A = (C, E)

where `C` is the ArchiScript category of nominal VDPs and Operations and `E`
is the selected finite presentation syntax.

The category need not retain expression syntax. A typed expression has exactly
one source and exactly one target,

    e : X -> Y

and denotes one ordinary `Operation X Y`.

An expression may still have tree-shaped syntax through composition, tensor,
copairing, and structural isomorphisms. A linear chain is only one special
expression shape.

An expression family is finite and nonempty. Every expression in one family
shares one source; targets may differ. Source/terminal roles are relative to the
family and do not create new VDP kinds.

## Normalization is local and certified

0.5.0 does not require a complete whole-architecture isomorphism theory.

For expressions with unchanged endpoints, a rewrite is admissible when their
semantic Operations are equal.

When a structural rewrite changes endpoint representatives, correctness is a
commuting square induced by explicit `PartitionIso` witnesses.

The first normalizer API therefore exposes proof-carrying local rewrites rather
than a global search for a minimum presentation.

Normalization must not silently delete nominal VDP boundaries. Composition
creates a composite morphism but does not remove its intermediate object from
the category.

If a derived view intentionally hides a nominal intermediate VDP and keeps only
selected endpoints, the selected architecture has been reduced. Call that an
**architecture projection**, not normalization. 0.5.0 records this distinction
but does not introduce a foundational projection object.

## Distributivity

The structural equivalences

    (A tensor R) coproduct (B tensor R)  ~=  (A coproduct B) tensor R

and

    (R tensor A) coproduct (R tensor B)  ~=  R tensor (A coproduct B)

must be implemented as concrete `PartitionIso` witnesses, with naturality for
Operations, before they are available as normalization certificates.

This is binary distributivity only. The nonempty VDP calculus still has no
initial VDP, so do not claim arbitrary finite coproduct structure with zero.

## Dependency and reachability observations

Tensor and coproduct retain different meanings.

- tensor: independent simultaneous coordinates;
- coproduct: tagged alternatives;
- refinement/coarsening: intentional same-carrier loss of resolution.

A tensor factor in the materialized family source can be an independent
dependency. A VDP merely occurring as another coproduct summand is not thereby
a dependency.

Coproduct laws may simplify a selected expression, for example

    [f,g] . inl = f

without globally deleting the unused summand from the architecture.

Identify dependency before provenance. A family may depend on a current VDP
value without depending on one particular producer family.

Cycles are allowed. Every selected expression remains finite; the release does
not enumerate all finite traversals of cyclic categorical closure.

Graphs remain derived views of already-defined dependency, provenance, or
reachability relations.

## Stress coverage

`ArchiScriptExamples/ReservationController.lean` remains the canonical
repository stress test. 0.5.0 extends it to cover:

- sequential composition;
- independent tensor;
- design-time coproduct;
- partial operations;
- coarsening;
- successful and rejected factorization;
- expression syntax and denotation;
- one-source / multiple-target expression families;
- distributive source factoring;
- local normalization certificates;
- the distinction between expression normalization and architecture projection.

Isolated examples and API smoke tests may explain individual constructors, but
new public calculus features must also be integrated into this stress model when
their meaning genuinely occurs there.

## Non-blocking questions

The following do not block the 0.5.0 foundation:

- generator versus derived-alias presentation metadata;
- flat versus structural dependency result shapes;
- mathematical set versus finite indexed implementation of expression families;
- shared-subexpression representation;
- summand-level versus member-level reachability / producer precision;
- deterministic global rewrite orientation and cost model;
- whole-architecture equivalence for transformations that change nominal
  boundaries or family structure.

Resolve these from concrete use cases rather than adding ontology in advance.

## Explicit non-goals

0.5.0 does not:

- make tensor a categorical product;
- add Trigger, Terminal, Resource, MutableResource, ExternalVDP, Loop, Cycle,
  Scope, Reach, or dependency-edge primitives;
- infer runtime scheduling, ordering, parallelism, transactions, or I/O counts;
- treat coproduct as coarsening;
- treat coarsening as architecture isomorphism;
- remove nominal VDPs under the name of normalization;
- require a graph representation;
- promise a globally minimal presentation;
- settle whole-architecture isomorphism before it is needed.
