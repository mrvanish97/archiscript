# Next-version backlog after the 0.7 semantic rewrite

## Whole-inventory orphan/SCC diagnostics and coverage accounting

Inspect the entire declared Node/VDP and Generator/Operation inventory alongside
Causes. Detect isolated nodes, unused declarations and rootless SCCs, including
components absent from every Cause-starting traversal. Distinguish canonical
rooted production from nominal ownership, cyclic markers, empty supplier images
and unobservable status. Report intentional exclusions/dead declarations
separately from unexplained orphans; retain author dispositions.

Prioritize a useful diagnostic when feasible, with the accepted counterexamples
in `SourceCoverage.sourceOnly` and `UngroundedCycle.certified` as regressions.
Also cover an unrelated owned SCC obstructing an observable Cone's structural
boundary proof. State the diagnostic's assurance scope; it is not by itself a
global semantic coverage theorem. In 0.7.0 this remains manual author review,
with explicit assumptions in model handoffs.

## Automatic all-generated-Expression/Cone coverage

**0.7 status: NOT AUTOMATICALLY VERIFIED.**

Prove that every finite linear Expression generated from the closed primitive
inventory, including paths beginning inside cycles and justified tensor imports,
is covered by at least one declared one-Cause Cone. The current certificate
quantifies over derived local contexts and checks complete terminal boundaries;
it does not prove this additional universal union-of-Cones property.

This stronger obligation is separate from inventory diagnostics: a traversal of
only Cause-generated Expressions can miss a rootless component entirely. Neither
check substitutes for the other. A walk over nominal VDP values is insufficient:
equal denotations do not identify
occurrences, and recursive cross-Cone supplier derivations retain histories.
A candidate symbolic checker needs a precise `GeneratedExpression`/`InCone`
relation, induction/coverage proof, disconnected-cycle and omitted-generator
negative cases, and a sound connection to the existing root-instance semantics.
Real-world inventory completeness remains an author assumption even after this
relative theorem is proved. Do not replace it with a selected family or list.

## Committed 0.8.0 deliverable: cyclic tensor P/E inside one Cone

**PLANNED / NOT YET DEMONSTRATED in a complete Lean regression.**
The project commits to supporting a `Request ⊗ State` input
where `State VDP` is also produced by an internal feedback
route **within one Cause and one Cone**. The present ArchiScript
API may already be sufficient; **we have not yet established
that by constructing and verifying this exact case**.
First attempt the model with existing primitives; if the
experiment exposes missing checks or insufficient provenance
analysis, implement the required changes. **0.8.0 is the
target release**; retain the feature as an explicit
future-version commitment if staging is required. This
commitment is not evidence of current formal support.

This ASCII diagram is part of the intended explanation
and must remain in the [README FAQ](../README.md#can-one-cone-analyze-conflicting-or-concurrent-resource-states-through-a-cyclic-tensor)
as well:

```text
                          ONE CONE
                             |
                  Cause: webhookArrived
                             |
                             v
                        Request VDP
                             |
                             v
      +----------------------------------+     +------------------+
      |      Request VDP x State VDP     |<----|     State VDP    |<--+
      |            tensor input          |     | possible members |   |
      +-----------------+----------------+     +------------------+   |
                        |                                           |
                        v                                           |
                    Operation(s)                                    |
                    /          \                                    |
                   v            v                                   |
             Decision VDP     State VDP (updated) ------------------+
                   |            |
                   +------+-----+
                          |
                          v
          EFFECT: Decision VDP x State VDP
          (terminal + typed cyclic observation boundary)
```

**Meaning:** There is a single `webhookArrived` Cause.
`State VDP` denotes the same declared semantic partition
at two *occurrences*: an input tensor factor and a
feedback-produced result. The diagram does **not**
postulate new Causes, runtime steps, physical clocks,
or a particular initial storage-state value. An actual
model must explicitly supply the Operations (including
any fan-out), their rooted suppliers and the typed
cyclic route. An Operation cannot silently return two
independent results. The proposed Effect is the
**intended** tensor of a terminal Decision and a typed
cyclic State observation: it is valid only if those
precise Effect coordinates are derived and proved by
the provenance machinery.

**Mandatory delivery/acceptance criteria:**

1. **Positive complete Lean example:** add a dedicated
   example such as `ArchiScriptExamples/CyclicTensorCone.lean`.
   Declare one Cause, the complete meaningful Request
   and State partitions, genuine generator inventory,
   an Operation consuming `Request ⊗ State`, a State-
   producing feedback route and a real
   `Term.CycleBoundary` with one entry hole and explicit
   auxiliary factors. Obtain a **non-vacuous**
   `CertifiedDeclaredArchitecture` proving
   `effectCoverage`, `inputSources`, all universal
   `inputs`, `cones`, and `boundariesComplete`.
   Pass the normal Lean and proof-audit verification gate.
2. **Cyclic tensor input completeness (P and E):**
   for **every supported coherent occurrence** of a
   tensor-consuming generator, including arbitrarily
   many finite cyclic unfoldings, prove
   `ReachInput(g,t) = AdmInput(g,t)` over the full
   tuple relation (E), and for each input coordinate
   prove that the independently incoming image
   **equals the projection of admissible tuples** (P).
   Every genuinely incoming Request member must
   have a reachable/admissible State partner, and
   symmetrically for independently incoming State
   members. Do **not** assume every selected VDP
   member is an incoming member, and do **not**
   require all Cartesian cross-pairs to be reachable.
3. **Rooted supplier provenance:** verify all actual
   State and Request suppliers, `RootCoherent`,
   `InputSources` and source availability. The
   same Cone may contain the relevant grounded route;
   no fixed **value** for an initial State is required
   to state the theorem. A rootless feedback-only
   strongly connected component, however, must not
   generate incoming members by fiat. Preserve the
   existing `input_partner` theorem's independent
   `supplierImage` premise.
4. **Effect completeness and provenance:** derive
   actual terminal Decision and cyclic State boundary
   coordinates, rather than inferring them from
   nominal VDP equality or this diagram. Prove
   exact complete Effect tuples, P-style coordinate
   images and the cyclic `EffectProvenance`
   conditions under justified common worlds and
   declared contexts. Ensure the Effect is nonempty.
5. **Negative regressions:** reject a missing State
   supplier, a rootless feedback cycle posing as
   reachable, impossible asserted tensor pairs,
   a marginal image without a joint partner,
   mismatched cyclic provenance and incomplete
   saturation/closure. Also preserve positive
   correlated tuples across multiple unfoldings.
6. **Algorithm review/repair:** check whether current
   `derive_provenance`, finite normalized-history
   cache, `effectCoverage`, contextual input `P/E`,
   and source accounting already cover the combined
   cyclic tensor. If sufficient, demonstrate the
   complete proof. Otherwise improve the checker,
   give soundness/completeness arguments, and add
   regression tests. Do not confuse bounded fuel,
   finite VDP members, or an apparently stable
   terminal image with proven closure.
7. **Assurance boundary:** support architectural
   analysis of *a priori competing resource states*,
   not implicit simulation of two physical workers.
   A separate temporal model is **not necessary**
   for the semantic `Request ⊗ State` problem,
   but real atomicity, linearizability, eventual
   delivery, and deployed behavior require their
   own justified contracts or implementation checks.

## Important 0.8.0 research goal: one VDP reused by N distinct Cones

**Formal foundations and consequences first; NOT YET PROVED or
automatically certified as shared-state concurrency.** Investigate
the more general **non-cyclic, cross-Cone** case in which two, three
or an arbitrary finite number `N` of distinct Causes/Cones interact
with a single *declared State VDP*. This is a **separate research
goal** from the committed single-Cone cyclic-tensor regression
above. Do not solve it by hard-coding `A ⊗ B`, inventing a new
`Resolve` Operation for every set of events, or multiplying all
`N` event VDPs into one ever-growing input tensor. Seek a
compositional, scalable account in **the existing ArchiScript
language**, if its semantics suffice. Introduce a new primitive
only if a concrete counterexample proves the existing vocabulary
insufficient and the new rule's obligations can be justified.

The conceptual shape to investigate (not a currently certified
architecture) is:

```text
  Cause A -> Cone A -> Operation A ----+
  Cause B -> Cone B -> Operation B ----+--> same declared State VDP
      ...                             |      (shared semantic role?)
  Cause N -> Cone N -> Operation N ----+

  Multiple arrows to a VDP do NOT, on their own,
  join writes, arbitrate conflicts, share a physical
  storage cell or produce one combined state.
```

**Crucial hypothesis: the reachable/admissible member images need
NOT coincide across Cones, even when the output VDP is the same.**
The VDP's selected partition members remain one fixed family;
what can differ is the image of a specific producer occurrence,
under its Cause, boundary and context. For example:

```text
   Cone A -> State VDP     Cone B -> State VDP
             {Free, Locked}         {Locked, Done}
                    |                    |
                    +--------- tensor ---+
                                |
                        State VDP ⊗ State VDP
                   (two provenance coordinates)
```

Here the braces indicate **possible incoming/output member
images for each Cone**, *not* different definitions of the
State VDP and not two physical versions of one mutable cell.
A possible **explicitly justified** joint contract could be
`R = {(Free, Locked), (Locked, Done)}`; it preserves
each factor's image as a projection without asserting all
four Cartesian pairs or requiring equal values.
No `R` is automatically justified merely by drawing the
tensor. If an actual consuming generator uses both suppliers,
its contextual P/E must establish full `Reach = Adm`
and exactly these marginal partner images. A standalone
analytical Effect has its own provenance/tuple obligations,
not an implicit join Operation. In particular,
**different outputs are not an automatic write conflict,
and identical outputs do not prove the same resource
was accessed**.

For `N` Cones the analogous inquiry is about a
family `I_c` of **potentially different** producer images
and a justified admissibility relation over their
occurrences, rather than imposing `I_c = I_d` for all
Cones. Investigate a compositional representation,
provenance-sensitive restrictions and coverage proofs
without requiring one hard-coded `N`-ary merge.
Do not mistake projection coverage for arbitrary
pairwise or global joint reachability.

**Questions that 0.8.0 must settle**

1. **Identity versus type.** Define precisely what it means
   for different Cones to reuse *the same VDP* rather than
   merely have distinct Nodes with equal `Partition`
   descriptions. A `VDP` is a semantic partition, **not
   automatically the identity of a shared mutable resource**.
   The current `ArchitectureSignature.owner : Node → Cause`
   gives each Node one owner; `Term` and
   `RootCoherent` preserve concrete supplier origins.
   Investigate how one genuinely common state role could
   be declared/referred to from multiple owned Cones
   **without erasing occurrence identity, ownership, or
   Cause-rooted provenance**. Determine whether existing
   cross-Cone imports, shared Nodes, contexts and `World`
   express the intended interpretation, or whether an
   explicit sharing/identity relation with proofs is
   indispensable.
2. **Several producers versus one result.** Distinguish
   *multiple independent Operations that may produce
   members of the same VDP* from a theorem that they
   jointly update one resource or select one resultant
   member. Two incoming arrows, equal VDP carrier types,
   Effect tensors and coproducts do **not** imply
   merging, last-writer-wins, mutual exclusion, or an
   implicit `Operation.run` with nondeterministic choice.
   Identify the exact additional relation or declared
   consequence required for any claimed joint outcome.
   Prefer an existing `Operation`/context/contract
   construction where fully justified; do not smuggle
   in hidden branch-selection or imaginary suppliers.
3. **Compositional N-way semantics.** Investigate a
   statement parameterized by any finite family of
   distinct declared Causes, Cones and their supplier
   occurrences, rather than a separate manual `N`-ary
   Operation per set of events. State which pairwise
   or local proofs, if any, compose into sound
   N-way admissibility/provenance guarantees, and
   produce counterexamples where pairwise consistency
   does **not** imply joint tuple consistency.
   The current closed finite Cause inventory and
   single canonical root per Cause must not be
   confused with an arbitrary number of **runtime
   invocations** of that Cause.
4. **P/E and Effect interaction.** Test how independently
   incoming shared-state members, admissible joint
   tuples, contexts, `InputSources`, full `Reach=Adm`,
   `EffectProvenance`, ownership and terminal
   coordinate histories behave when different Cones
   refer to the same State VDP. Reuse nominal values
   only where justified by the exact **producer
   occurrence**, not merely the VDP name. Establish
   whether shared-state constraints can be written
   without requiring one universal global tensor of
   all events or falsely inferring physical
   simultaneity from a common `World`.
5. **Safety against new backdoors.** Explicitly search
   for derivations that would accept: an ungrounded
   shared State member; two independently supplied
   outcomes treated as one chosen result; a missing
   supplier masked by another Cone's same-typed VDP;
   false global admissibility from pairwise P/E;
   conflation of different resource identities;
   loss of owner/root history; or an unstated
   write-conflict policy. Any proposed relaxation
   must come with a precise formal contract,
   soundness argument and failing negative tests.
   No automatic "merge" or exclusivity may be
   inferred solely from reuse of a VDP.
6. **Concrete research deliverables:** write down a
   candidate semantics and its exact assurance
   scope; build a minimal **two-Cone counterexample**
   and a positive cross-Cone shared-VDP example,
   then a small parameterized/family-based or
   three-Cone regression demonstrating what
   scales and what fails. Compare results against
   [`CrossCone.lean`](../ArchiScriptExamples/CrossCone.lean),
   [`CorrelatedJoin.lean`](../ArchiScriptExamples/CorrelatedJoin.lean)
   and the one-Cone cyclic-tensor regression.
   Document if the present calculus is already
   sufficient, sufficient only with stronger
   author proof obligations, or needs a new
   justified formal rule. **Do not announce
   automatic N-way shared-resource verification
   without a corresponding Lean theorem and tests.**

**Boundary of this goal:** the first deliverable in 0.8.0
is a **rigorous mathematical account of sharing and
cross-Cone composition**, including any discovered
unsound shortcuts, not a promise that physical
concurrent writes, database atomicity, serialization
or an unbounded runtime event history will become
automatically verified. An external clock is not
a prerequisite to express a priori semantic
conflicts; conversely, shared VDP membership alone
does not prove physical resource identity or
the correctness of racing writes. Preserve
this distinction throughout the investigation.

## Coproduct semantic-use discipline and guarded architectural alternatives

**0.7.0 status: coproduct algebra is proved; the intended architectural use
of every coproduct is NOT AUTOMATICALLY VERIFIED.** See the
[FAQ on alternatives versus independent supplier branches](../README.md#can-a-coproduct-combine-two-independent-supplier-branches-into-one-alternative-response)
and the matching author/reviewer rule in
[`skills/archiscript/SKILL.md`](../skills/archiscript/SKILL.md).

For 0.8.0, investigate a **precisely scoped, enforceable guard** against
misusing a coproduct as an implicit logical OR, arbitration mechanism or
hidden branch between independently produced Operations. Preserve
`Partition.coproduct` as the *tagged-sum carrier/member construction*
and preserve legitimate injections, `copair` and coproduct algebra on
already tagged semantic inputs. Do **not** turn coproduct into an
`Architecture.Inputs` constructor that silently merges separate
suppliers, and do not prohibit valid alternative input or output types.

Concrete acceptance cases and proposed obligations:

- **Allowed declared boundary alternatives:** one input whose carrier
  is `Sum Nat String` (a request is a number *or* a string), or one
  output whose carrier is `Sum SuccessPayload ErrorPayload`
  (a response is success *or* error), with justified selected Subdomains
  and the existing finite, inhabited, disjoint, covering VDP proofs.
  A coproduct's coverage theorem is **relative to its declared sum
  carrier**; a real API's completeness remains an external assumption.
- **Allowed tagged handling:** an Operation maps a semantically
  distinguished input member to a defined `Sum.inl` or `Sum.inr`
  result, or `copair` consumes an *already tagged* alternative.
  Its source distinctions, tag provenance and partiality must remain
  explicit; no new nondeterministic choice is inferred.
- **Rejected implicit sum join:** two independent producers or
  Operations, one reaching a success-shaped VDP and one an
  error-shaped VDP, are not automatically mutually exclusive and
  cannot become one selected response by a coproduct alone.
  A common Effect tensor is not an implicit choice; an actual
  response-producing Operation and justified supplier route are
  still required.
- **Separate tensor regression:** `Request ⊗ ServiceStatus` can feed
  one response VDP with a success/error coproduct carrier.
  `(Invalid, Available)` and `(Invalid, Unavailable)` may both map to
  `InvalidInput`, but that proves **value-level output invariance**,
  not absence of the status supplier or execution ordering.
  Keep P/E verification and defined output mapping distinct.

Candidate 0.8.0 deliverable: define an audit/checkable declaration or
restricted architectural surface that records **where** a sum is used
(as a boundary/VDP alternative versus claimed producer combination),
**which evidence identifies the tag**, and **which declared Operation
actually produces a tagged result**. Add small positive and negative
Lean/regression examples for the cases above, and ensure any rejection
diagnostic cites the precise checked rule. Before claiming automatic
enforcement, state and prove the actual soundness/scope of the guard;
avoid a syntactic ban that rejects valid `copair` or legitimate
`Sum`-typed carrier choices.

**Limit:** neither a generic Lean theorem nor syntactic inspection can
establish that the architect's chosen `Sum` carrier truthfully represents
all real-world possibilities or that a deployed implementation obeys it.
If 0.8.0 can enforce only the structural part, report the remaining
semantic-intent and external-adequacy checks as **MANUAL / NOT
AUTOMATICALLY VERIFIED**. Do not silently promote an audit convention
into a full architecture-correctness guarantee.

## Optional analysis improvements

- Derive maintainable finite exact abstractions for larger provenance-sensitive
  fragments. Prove their query agreement; do not infer finite state from finite
  VDP members. The current bounded saturation returns an exact result only once
  closure is checked. SCC/worklist optimization needs a preservation proof.
- Provide ergonomic proof combinators for universal context and terminal
  occurrence obligations without removing required proof fields.
- Profile provenance-cache closure and catalog lookup on at least two realistic
  inventory sizes before choosing an index or worklist optimization. Repeated
  full-list scans are a possible cost, not a measured slowdown. Any replacement
  must preserve normalized histories, source positions, closure checks and proof
  coverage; retain small semantic regressions independently of benchmark sizes.
- Improve witnessed diagnostics for nondecidable semantic contracts while
  preserving the distinction between an unsolved proof and an invalid model.
- Explore a frontend only after the semantic API is reviewed. No Markdown parser,
  generated theorem language, scheduler, resource calculus or implementation
  conformance claim is implied by this backlog.

The 0.7 shared-target correction is implemented, not deferred here: finite
normalized-history bases require seeds, full-source closure and realizations;
shared suffixes retain distinct histories. Future analysis work may broaden
that supported fragment to more general cyclic
observation quotients, with soundness/completeness proofs. None of that work
reintroduces named unique VDP uses, cloned graphs or generator-output uniqueness.

The 0.7 input-source and no-observation cases are also implemented: each declared
generator has a mandatory source-accounting obligation, and each Cause has an
observable or explicitly unobservable status. Infinite root-instance types do
not require infinite caches: only each concrete Cause's canonical origin is
supported. Composition of repeated external invocations would be a separate
future extension, with its own semantics.
